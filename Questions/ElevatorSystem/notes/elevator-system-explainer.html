02 — Design Patterns Used
🔒
Singleton

ElevatorController

Only ONE controller exists for the entire building. Built using a private constructor + getInstance() method. Building fetches this singleton instead of creating a new one.

🔧
Strategy

SchedulingStrategy

The scheduling algorithm is pluggable. You can swap LOOK → FCFS → SCAN at runtime by calling controller.setSchedulingStrategy(...) without touching Elevator or Controller code.

📨
Command

ElevatorRequest / ElevatorCommand

Every request (internal or external) is an object with an execute() method. Requests can be queued, logged, undone, or replayed — just like real command pattern.

👁️
Observer

ElevatorObserver (scaffolded)

Elevator is the Subject. When it moves floors or changes state, it can notify observers like a display panel or door controller. The hooks are commented-in ready to activate.

03 — How To Write It (Mental Flow)
01

🏗️ Start with Enums & Simple State

Before any class, define what states and directions exist. These are the vocabulary of your system — everything else references them.

enum Direction { UP, DOWN, IDLE }
enum ElevatorState { IDLE, MOVING, STOPPED }
02

🏢 Build the Domain Models

Define the physical world: Floor (just holds a number), Elevator (id, currentFloor, direction, state, request queue), and Building (name, floors, controller reference).

// Elevator holds its own queue
class Elevator {
  int id, currentFloor, totalFloors;
  Direction direction;
  ElevatorState state;
  Queue<ElevatorRequest> requests; // LinkedList
}
03

📨 Define Requests (Command Pattern)

Use an abstract base class ElevatorRequest that implements ElevatorCommand. Then create two concrete types: ExternalRequest (from a floor panel) and InternalRequest (from inside the elevator).

interface ElevatorCommand { void execute(); }

abstract class ElevatorRequest implements ElevatorCommand {
  String requestId; RequestType type; long timestamp;
  abstract int getFloor(); // used by strategy
}

// External: floorNumber + direction (pressed UP/DOWN on a floor)
// Internal: elevatorId + destinationFloor (pressed inside cabin)
04

🔧 Define the Strategy Interface

The strategy only needs to answer one question: given this elevator's current state and request queue, what floor should it go to next? Keep the interface minimal.

interface SchedulingStrategy {
  int getNextStop(Elevator elevator);
}

// LOOK: sweep UP serving all above, then reverse DOWN
// FCFS: just serve requests in arrival order
// SCAN: like LOOK but goes all the way to top/bottom
05

🧠 Write the ElevatorController (Singleton)

This is the brain. It holds all elevators and the strategy. It exposes two key methods: requestElevator(floor, dir) for external calls, requestFloor(elevatorId, floor) for internal. Then step() advances the simulation — each elevator asks the strategy for its next stop and moves there.

// Singleton getInstance()
public void requestElevator(int floor, Direction dir) {
  ExternalRequest req = new ExternalRequest(...);
  Elevator best = findBestElevator(req); // dispatch logic
  best.addRequest(req);
  req.execute();
}

public void step() { // advance simulation 1 tick
  for (Elevator e : elevators) {
    int next = strategy.getNextStop(e);
    e.moveToNextStop(next);
  }
}
06

🔍 Implement LOOK Strategy

Split the request queue into two heaps: upQueue (min-heap, floors above current) and downQueue (max-heap, floors below). If moving UP, take from upQueue; if empty, switch direction. Same for DOWN. If IDLE, pick the nearest request.

// Partition requests by floor vs. currentFloor
PriorityQueue upQueue  = new PQ(ascending); // min-heap
PriorityQueue downQueue = new PQ(descending); // max-heap

if (dir == UP) → poll upQueue (or switch to DOWN)
if (dir == DOWN) → poll downQueue (or switch to UP)
if (dir == IDLE) → pick nearest of both queues
07

🚀 Wire it in Main

Create a Building → get its ElevatorController → send requests → call step() to advance the simulation. The Building creates the controller singleton internally, so main stays clean.

Building b = new Building("TechTower", 10, 2);
ElevatorController ctrl = b.getElevatorController();

ctrl.requestElevator(3, Direction.UP); // external
ctrl.requestFloor(1, 7); // internal
ctrl.step(); // moves elevators to next stops

05 — Key Insights to Remember
💡 Why Singleton for Controller? There should only ever be ONE brain managing all elevators in a building. If two controllers existed, they'd assign the same elevator to conflicting floors. Singleton enforces this.
💡 Why Strategy Pattern for Scheduling? Different buildings need different algorithms. An office building (morning rush all up, evening rush all down) behaves differently than a hospital. Swapping the strategy object at runtime changes the elevator's entire behavior with zero code duplication.
⚠️ Elevator's queue is a plain LinkedList The strategy re-partitions it on every step() call using PriorityQueues internally. The elevator itself doesn't need a sorted queue — the strategy handles ordering logic.
📌 LOOK vs SCAN SCAN goes all the way to floor 1 or floor 10 before reversing, even if no requests are there. LOOK reverses as soon as there are no more requests in that direction. LOOK = smarter, fewer empty trips.
💡 findBestElevator() logic Prefer: idle elevator closest to the requested floor → or an elevator already heading the same direction. Fallback: closest elevator regardless of direction.
⚠️ Observer is stubbed out The Elevator class has the hooks for notifyStateChange() and notifyFloorChange() already written — just commented. To activate a floor display panel, uncomment and implement ElevatorObserver.
06 — What You Could Add Next
🏭
Factory

SchedulingStrategyFactory

Create a factory that takes a String like "LOOK" or "FCFS" and returns the right strategy instance. Main.java can then read the strategy from config.

👁️
Observer

ElevatorDisplay / Door Controller

Implement ElevatorObserver with two methods: onFloorChange() and onStateChange(). Register it on the elevator to get real-time updates.

📋
Extension

FCFS & SCAN Strategies

Both are just new classes implementing SchedulingStrategy. FCFS = poll the head of the queue. SCAN = like LOOK but travel to top/bottom floor before reversing.

🚪
Model

Door, MaintenanceMode, Weight Sensor

Add a DoorState enum (OPEN/CLOSED) to Elevator. Add isUnderMaintenance flag. Add currentWeight to skip overloaded elevators in dispatch.
